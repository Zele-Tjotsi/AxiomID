# Contributing to AxiomID

AxiomID follows an engineering workflow designed to resemble a professional software organization.

## Before Implementation

Significant changes should begin with an appropriate design artifact.

Depending on the change, this may include:

- Product requirement
- Architecture Decision Record
- RFC
- Threat model
- API specification
- UX design
- Performance analysis

## Pull Requests

Pull requests should explain:

- What changed?
- Why was the change necessary?
- What alternatives were considered?
- How was the change tested?
- What security implications exist?
- What operational implications exist?
- Are documentation updates required?

## Engineering Standards

Contributions should prioritize:

- correctness
- security
- maintainability
- testability
- observability
- accessibility
- simplicity

## Commit Messages

Commits should describe a coherent change.

Prefer:

`docs(prd): define initial product scope`

over:

`update stuff`

## Design Before Code

AxiomID intentionally avoids implementing major functionality before the underlying requirements and architecture have been reviewed.

## Review

Changes should be reviewed critically before being considered complete.

A feature is not complete merely because it works locally.
